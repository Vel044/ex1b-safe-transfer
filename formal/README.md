# SFT1 协议模型检查

本目录验证 SFT1 选定的上传和下载状态机性质。TLA+ 模型是对源码的人工抽象，不是源码的自动翻译，也不是整个系统的安全证明。

## 复现

在项目根目录执行（Java 11+、Python 3.9+；首次需要访问 GitHub）：

```sh
python3 scripts/verify_protocol.py
```

脚本固定使用 TLA+ Tools v1.7.4（TLC 2.19），校验发布页的 JAR SHA-1，并将 SHA-256 写入结果。单 worker、固定 seed 和指纹多项式；每个配置最长运行 180 秒、Java 最大堆 1GiB。JAR 自动下载到本目录 tools/，不纳入源码仓库。

所有 18 个配置都必须符合预期才返回成功：9 个正确模型检查应无错误；6 个故意修改保护规则的模型应违反指定不变量；无公平性配置应违反最终完成；2 个可达性见证配置应找到完成状态。因此，部分 TLC 日志的非零退出码是预期结果，不应单独解释为协议缺陷。

## 模型和边界

- `SFT1Upload.tla`：初始化已完成后的上传，数据写入与 fsync、数据库检查点、ACK、完整性校验、正式链接提交、完成记录；另含断线或进程中断抽象、重连、暂停、取消、重复块和任务所有权守卫。
- `SFT1Download.tla`：客户端写盘、保存偏移、服务端 ACK、恢复时核对源文件和前缀、完整文件校验、FINISH 和本地提交。源文件变化及前缀错误只在离线阶段发生。
- SFT1Transfer.tla从两个已初始化任务出发，以不同符号表示 A、B 各两块内容。共用一条连接，允许一次断线；待处理请求占用不同的编号。请求集合和响应集合允许任务交错，省略底层字节流。每个任务只推进一个块，断线清除未完成请求，按接收方持久检查点恢复。下载 ACK 往返及最终校验提交分别合并为一个动作；同时活动请求编号从两个符号中选取。
- 三个正常 transfer 配置分别覆盖双上传、双下载及一上一下。检查临时内容始终是本任务源文件的前缀、确认进度不超过检查点、已提交文件内容正确，并在重连与推进弱公平的假设下检查两个任务最终完成。transfer_mutant_wrong_reply 仅放宽响应匹配守卫，用同偏移的下载请求检验任务归属。
- `results/*.log`：完整原始输出；`results/summary.json`：命令、退出码、状态计数、源文件散列及环境。
- `*.cfg`：有限参数和实际检查的性质。没有状态剪枝或深度截断；正确配置使用默认广度优先遍历直至队列清空。反例配置在首次违例时停止。

上传单任务 3 块、双任务各 2 块、空文件 0 块；每个任务至多一次故障。下载单任务 3 块、至多一次故障。原上传双任务配置只检查不同任务的交错，未建立共享目标、配额、连接槽、令牌桶等资源模型。所有权抽象为 owner 布尔参数，不模拟证书或账户数据库。

TLS 及哈希算法被抽象为可信通道与身份比较结果。不模拟 TCP 报文字节、消息解析器、32 位请求编号回绕、目录操作、心跳计时、无限规模、磁盘损坏、掉电一致性、操作系统原语失败及提交期间取消。`CHECK_DEADLOCK FALSE` 用于允许完成、失败、取消和身份校验拒绝后的静止状态，不能据此宣称无死锁。活性在禁用取消、暂停、损坏和源变化后，额外假设故障次数有界、重连与推进动作弱公平。

安全条件的守卫由人工从实现提取；检查通过表示这些抽象规则在限定状态空间中满足所列性质，不能证明实现完全遵守模型。报告另列实际测试作为补充，未进行模型到源码的 refinement 证明。
